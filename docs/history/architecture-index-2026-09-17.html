desk-pet 架构整合方案决策草案

Hermes 大脑 + Electron 壳 + Rust 性能件 + 旧版体验层回迁。整合 Cyrene 框架的工作模式、Hermes 的 Agent 循环与学习进化机制、旧版自研的 L0-L3 分层记忆与情绪/互动/语音资产。
版本 v1.0 日期 2026-09-17 状态 待 PoC 验证后转正式 适用仓库 huankun05/huankun05-desk-pet

1背景与问题

旧版 desk-pet-old（273 commits，Tauri 2 + React 19 + Python）：自研桌宠，"身体很全、脑子很浅"——L0-L3 金字塔记忆、情绪/人格状态机（PAD+激素）、本地真人声（CosyVoice 纳西妲微调）、互动低频聚合沉淀、摄像头感知。但 Agent 循环是"玩具级"，且打包一直未完成。

当前 desk-pet（345 commits，Electron 43 + TS + Pixi.js）：2026-09-03 整体迁移到第三方开源底座 Cyrene-Agent（Playa-0v0/Cyrene-Agent），Agent 能力直接到工业级（CyreneHarness、L0/L1/L2 记忆、DMAE Worldbook、RAG/MCP/Skill、多渠道），迁移后 71 commits 补齐了技能系统、LSP、凭据加密、i18n、QQ/NapCat 等。

驱动本方案的三个问题

  1. 大脑信任度：CyreneHarness 从未被充分测试（第三方个人项目，迁移后 71 个提交里修复了大量上游 bug：端口漂移、白屏、设置面板无法点击等）；而 Hermes Agent 实际使用过、行为可预期，且持续活跃维护（32.1k stars，最新 patch v2026.9.11，单版本窗口 5,139 个非 merge 提交）。
  2. 性能诉求：希望热点计算原生化。实测 Agent 循环是 I/O 密集（瓶颈在网络延迟），真正热点在混合检索（BM25+reranker，现为纯 JS）、Embedding 推理、音频处理——这些适合 Rust 局部替换，而非整体重写。
  3. 旧版资产平衡：旧版独有能力（L0-L3 记忆、情绪耦合、互动沉淀、CosyVoice 语音）在迁移后零残留（实测关键词 0 命中），需要在新架构中接回并平衡。

4记忆分层设计（L0-L3 平衡）

核实结论：旧版自研 L0-L3 金字塔记忆确认存在（server/hermes_core/memory/fragment.py，注释"借鉴 TencentDB Agent Memory 的 L0-L3 金字塔"）。新版 Cyrene 为 L0/L1/L2（无 L3）。Hermes 原生记忆层级与旧版金字塔语义一一对应，因此采用"L0-L3 作为组织规范保留，实现落位 Hermes 原生，差异化字段作增强层"。

4.1 旧版金字塔定义（资产盘点）

L3 · persona 长期用户画像learning_scheduler 聚合 · Honcho 语义对应
L2 · scene 场景块（话题簇聚合）librarian 按层召回 · 摘要/压缩语义对应
L1 · 原子事实fact/preference/rule/feedback/event + persona/episodic/instruction 子类型
L0 · raw 原始对话片段scribe 保留 N 条原文 · state.db 语义对应

配套机制：decay.py 遗忘曲线、is_permanent 永久标记、按层召回过滤，以及最独特的 emotion_snapshot（记忆创建时的整轮对话平均 PAD 情绪快照）。

4.2 三套体系对照与映射

层级旧版（自研）Hermes（目标实现）落位方式
L0raw 原始对话片段state.db（messages + FTS5 全文索引）零转换旧版 hermes_state.db 格式与 Hermes 一致（schema 已实测核对）
L1原子事实 + 子类型Honcho 记忆条目 + FTS5 召回碎片导出映射为记忆条目，保留 category/mem_type
L2scene 场景块聚合LLM 摘要 / 压缩 / 会话聚类learning_scheduler 聚合语义由 Hermes 调度承担
L3persona 长期画像Honcho 用户建模碎片 persona 类导入 Honcho 画像

4.3 旧版差异化增强层（Hermes 没有，必须保留）

增强点说明实现形态
emotion_snapshot记忆条目附加创建时 PAD 情绪快照，"角色记得当时的心情"记忆条目扩展字段，随导入/写入附带
is_permanent永久记忆跳过遗忘曲线映射到 Hermes 记忆的 permanent/pin 语义
按层召回L0-L3 过滤注入（按场景选择注入层级）Hermes 记忆检索侧做 layer 过滤适配层
sensitivity 分级（建议新增）public / private / secret 三级，控制记忆是否可跨渠道/被脱敏记忆条目附加字段，配合 Hermes redact 脱敏
平衡原则：每种记忆只有一个主人——会话历史归 state.db、画像归 Honcho、技能归自进化系统、情绪耦合与互动沉淀作为附加层挂载，不另建第二套记忆库。

5安全等级：工具权限审批体系（D6）

用户确认："安全等级"指工具权限审批。设计为三级静态分级 + 运行时上下文调整 + 双保险 + 审计，融合两侧现有资产：Cyrene 的 permission/bootstrap、runtime-policy（超时/token 预算）、side-effect-resolver（副作用账本）、uncertain-effect-guard；Hermes 的 tool_guardrails、redact 脱敏、authz_mixin、credential_pool。

5.1 三级安全等级定义

等级策略典型工具判定依据
L0 · 自动放行auto-approve无需确认时间查询、搜索、读文件、skill_list、会话回忆只读、无副作用、无敏感数据
L1 · 确认执行ask弹窗确认写文件、网络请求、发消息、运行脚本、安装依赖有副作用但可逆、影响面可控
L2 · 高风险confirm-critical双重确认 / 可配置 deny删除/覆盖文件、凭据读写、任意命令执行、系统配置修改不可逆、影响系统、涉及敏感数据

分级依据两个静态信号 + 一个运行时信号：①工具声明的副作用类别（读/写/网络/执行/凭据）；②操作目标（文件路径、URL 域、进程范围）；③运行时上下文（当前工作模式、用户在场状态——Chat 模式默认更严，Work 模式可放宽）。

5.2 双保险执行流

① Hermes tool_guardrails静态规则第一道过滤：危险参数模式、路径白名单、命令黑名单
→
② 等级判定按 5.1 信号路由到 L0/L1/L2
→
③ Electron 审批 UIL1 弹窗确认；L2 双确认（工具名/参数/风险说明/一次或永久授权）
→
④ 副作用账本全量记录：调用方/参数/审批结果/耗时，可回滚提示
  • 授权记忆：支持"本次会话记住"与"永久记住"（可随时在设置面板撤销），永久授权进入加密存储。
  • 凭据安全：LLM/搜索/渠道密钥走 safeStorage 加密（复用迁移后已完成的凭据加密模块），Hermes 侧 credential_pool 管理轮转。
  • 消息脱敏：跨渠道/日志输出前经 redact 脱敏（已移植），sensitivity=secret 的记忆条目不进入可跨渠道上下文。
  • 超时与预算：沿用 runtime-policy 的超时/Token 预算策略，作为审批之外的第二层运行时护栏。

6服务接入设计

6.1 进程拓扑与协议

服务技术接入协议生命周期
Hermes Agent 大脑Python（PyInstaller 打包）WebSocket 本地回环（desktop channel）Electron 主进程 spawn，健康检查 + 崩溃重启
Rust 检索引擎Rust native addon（N-API）进程内同步调用，接口不变随主进程
Rust 音频引擎Rust 独立进程JSON-RPC over stdio（与截图助手 NDJSON 同模式）主进程托管启停
CosyVoice 语音 sidecarPython（唯一例外，torch 生态）JSON-RPC over stdio主进程托管启停，按需懒启动

6.2 关键接入点

  • Electron ⇄ Hermes：Hermes gateway 新增 desktop channel（其 gateway 本为多 channel 设计：Telegram/Discord/CLI，加 channel 是设计内扩展点），消息/事件/流式 token 走 WebSocket 本地回环，延迟可忽略。
  • 工具生态（MCP 桥）：Electron 侧保留的 Cyrene TS 工具（40+ 个）打包为 MCP server，Hermes 原生支持"客户端提供 MCP server"（v0.7.0+），工具资产零重写。
  • 工作模式：Chat/Work/Code/Learn 四种模式作为 Hermes 的会话级配置（系统提示 + 工具集 + 权限策略的绑定组），由 desktop channel 的 session 参数切换。
  • 渠道：飞书/微信/QQ 先在 Electron 侧保留现成适配并转发到 Hermes（保资产）；长期可迁移为 Hermes 原生 Python channel。
  • 情绪注入：Hermes 回复生成前注入当前情绪上下文（体验层状态机产出）；表情/语气联动在 Electron 侧消费情绪事件，双向往来。

7数据迁移路径

旧版数据处理方式工作量
hermes_state.db（会话历史）直接沿用/导入——schema 已实测为 Hermes 会话存储格式（sessions/messages/FTS5/gateway_routing/async_delegations），零转换半天（验证 + 索引重建）
memory/ 碎片数据（偏好/事实/规则）导出工具：碎片按 layer 映射——L1/L2 → Hermes 记忆条目，L3 → Honcho 画像；emotion_snapshot/is_permanent 随条目带走2-3 天
emotion.json（情绪/好感度/表情映射）直接导入 Electron 体验层状态机作为初始状态（favorability、人格、expressionMap 原样保留）半天
关键红利：旧版当年按 Hermes 思路建库，会话历史格式天然兼容——"关系资产"（你和角色积累的对话、回忆）不会随换底座丢失。

9风险与回退

风险缓解回退
Python 运行时打包回归（旧版痛点）PyInstaller 打包 Hermes 核心，官方有 packaging/installer 自愈支持；electron-builder 打壳，首次运行落地自用可先不打包，直接运行 Python 环境
Hermes "桌宠形态"未验证（GUI 审批/表情联动/流式 UI）PoC 先行，5 个验收点锁死；desktop channel 独立成模块PoC 失败退回 Cyrene 基线，损失 1 周
双栈调试成本（TS + Python）协议层隔离 + 统一日志格式（结构化 JSON）故障边界清晰，单侧可独立排查
Cyrene 工具资产在 MCP 桥下行为差异MCP 桥做兼容层，保留原有工具接口语义个别工具可在 Electron 侧直连处理
上游 Hermes 快速迭代导致 API 变动锁版本（v2026.x 固定），升级走变更评审协议层隔离，channel 适配器单点更新
