Cyrene-Agent 迁移评估报告

从自研 desk-pet（Tauri + Python 三栈）迁移到 Cyrene-Agent-master（Electron + 纯 TypeScript Agent）的可行性、得失与落地路径。结论先行：方向可行、收益巨大，但不是“换壳”，而是“以 Cyrene 为新底座重建 + 把 desk-pet 的差异化能力移植进去”。

评估日期：2026-09-03 ｜ 评估方式：双侧源码深度阅读（Cyrene README/package/orchestrator/memory + desk-pet README/PLAN/DEVELOPMENT/git log）｜ 非运行验证

1一句话结论

两个项目不是同一个量级的 Agent，而是“脑子”和“身体”错位互补。
Cyrene = 纯 TypeScript Electron 桌宠，“脑子”极深：工业级 Agent 主循环（CyreneHarness）、L0/L1/L2 分层记忆 + 自研 DMAE v5、40+ 工具、多厂商适配、飞书/微信/QQ 多渠道，测试覆盖 390 文件，打包链路已就绪。
desk-pet = React + Tauri(Rust) + Python 三栈混合，“身体”很全：本地真人声 TTS（CosyVoice 纳西妲微调）/STT/唤醒词、MediaPipe 摄像头感知、激素+PAD 情绪与 HEXACO 人格内在状态系统；但 Agent 循环仍是“玩具级” for 循环，记忆只有碎片级。

迁移到 Cyrene 一次拿到它整套“大脑”，代价是把 desk-pet 的语音/感知/情绪三条“身体”能力作为 sidecar 重新接回去——工程量的重心从“造轮子”变成“接插头”。

6迁移得失分析

“迁移” = 白得 Cyrene 的大脑 + 移植 desk-pet 的身体 + 丢弃双方重复且 Cyrene 更强的部分。

✅ 白得（Cyrene 强项，迁移即到手）

  • 工业级 CyreneHarness：checkpoint 崩溃恢复、副作用账本、mid-loop 压缩、双时钟超时、保守并行、大输出落盘
  • L0/L1/L2 分层记忆 + DMAE v5 + 冲突检测 + 实体图谱 + 记忆调度
  • 40+ 工具生态（fs/git/lsp/email/music/travel/document/web-search/run-shell/ast-grep）
  • 多平台渠道：飞书 / 微信 iLink / QQ NapCat —— 正好接上你之前的 QQ 机器人诉求
  • 多厂商分级适配 + reasoning + Structured Output，9 家模型厂商
  • RAG 混合检索 + reranker + 后台索引；MCP 生态；Skill 系统（snapshot/slash）
  • 主动聊天完整（状态感知 + 不打扰策略 + 多渠道投递）
  • 音乐陪伴（网易云 + 内置 mpv）、CLI 入口、场景模拟
  • 390 个测试文件 + 成熟 electron-builder 打包链路

⚠️ 失去（desk-pet 独有，迁移会丢）

  • 本地真人声 TTS：CosyVoice V3 纳西妲微调 / GPT-SoVITS / Edge（Cyrene 只有云端 API）
  • 本地 STT：FunASR / SenseVoice + VAD + 唤醒词
  • MediaPipe 摄像头感知（手部 21 点 / 面部 468 点）
  • 激素 + PAD 情绪 + HEXACO 人格漂移 + 昼夜节律 + 重逢引擎 + Archivist 整理
  • 番茄钟 / 每日问候 / 行为系统 / 多窗口悬浮布局
  • ServiceLifecycle 统一资源调度（大脑管身体的架构）

🔧 需移植（把“身体”接回 Cyrene）

  • 本地语音链路 → 作为 Python sidecar 子进程，由 Electron 主进程 spawn 托管
  • 摄像头感知 → 前端 Web 侧 MediaPipe 可行，注意 opt-in 隐私
  • 内在状态系统 → 二选一：改写为 TS 服务，或保留 Python sidecar
  • Live2D 渲染层重接 → Cubism v5 原生 ↔ pixi-live2d-display，模型 .moc3 通用可换
  • 角色模型与 persona prompt → 换模型 + 改写角色设定
  • 番茄钟/问候等小功能 → 低成本重写
可直接丢弃的部分：desk-pet 的 tool-loop（被 CyreneHarness 取代）、碎片级记忆体系（被 L0/L1/L2 取代）、自有 RAG/技能/主动/工具实现（Cyrene 更强）、MCP 管理（Cyrene 内置）。这些“旧轮子”不要搬，搬了反而是负担。

7推荐迁移路线（渐进，先跑起来再移植）

原则：先在 Cyrene 上跑通并确认“你想要的样子”，再逐模块移植，每阶段都可回退。
Phase 0 · 跑起来（约 1 天）
验证 + 对齐需求
  • npm ci（需 Node 24 + VS Build Tools + Rust 截图）
  • 配 LLM Key，验证 Chat / Work / Code 模式
  • 列出“我想要的样子”需求清单，划边界
Phase 1 · 底座定制（2–3 天）
建自己的版本基线
  • 复制为独立仓库 git init，建立基线
  • 换 Live2D 模型（纳西妲/昔涟/其他）
  • 改写 persona prompt 与界面外观
  • 配置自家 LLM / TTS 预设
Phase 2 · 移植身体（按优先级）
把 desk-pet 独有能力接回
  • P0：本地语音链路（TTS/STT/唤醒）sidecar 接入
  • P0：内在状态/情绪系统（若保留）
  • P1：摄像头感知（opt-in）
  • P1：番茄钟 / 问候等小功能
Phase 3 · 平台与打磨
对外与分发
  • QQ / 飞书渠道接入（承接旧 QQ 机器人）
  • 主动聊天调优、成本治理
  • electron-builder 打包分发

8风险与注意点

角色 IP / 授权
  • Cyrene 的昔涟模型是米哈游同人、非商用；desk-pet 的纳西妲同理
  • 自用可放心；对外商用两项目都受限
  • 换用模型时注意作者署名与授权范围
技术栈切换成本
  • Electron + 纯 TS 与 Tauri + 三栈差异大
  • 语音/感知/情绪是“重写接入层”而非复制
  • 需适应 Cyrene 的 IPC / 模块约定（90+ 通道）
上游更新与体积
  • Cyrene 迭代快，本地大改后 merge 上游会难——建议 fork 或只选关键更新合入
  • Electron 体积/内存大于 Tauri；Cyrene 已做优化，可关 Reranker/MCP 降内存
  • npm ci 需下载 Electron 等大依赖，网络要求
工程承接
  • desk-pet 的 273 次提交积累不能“直接搬”，要按模块评估价值
  • 建议把 desk-pet 冻结为“遗产仓库”，新开发全在 Cyrene 基线上

9待你拍板的关键决策

这些直接决定迁移工作量和“最终的样子”，建议开工前逐条定下来：
  1. 角色用谁？
    保留纳西妲模型？直接用昔涟？还是换其他 Live2D 模型？（决定模型与 persona 改动量）
  2. 语音走本地还是云？
    保留 CosyVoice 纳西妲微调等本地真人声，还是改用 Cyrene 的云 API（Mossland/MiniMax）？（决定 sidecar 工程量，这也是你最大的差异化资产）
  3. 摄像头感知要不要？
    手部/面部互动是 desk-pet 独有的交互卖点，但涉及隐私，建议 opt-in 默认关。
  4. 情绪/人格内在状态系统保不保留？
    这是 desk-pet 花大力气做的“灵魂”，Cyrene 没有，需要作为模块移植。
  5. 多平台要不要？
    QQ/飞书/微信 接入正好衔接你之前的 QQ 机器人项目，但要投入配置。
  6. “想要的样子”具体指哪些？
    外观/角色设定/功能清单/对话风格——越具体，Phase 1 越能一步到位。
