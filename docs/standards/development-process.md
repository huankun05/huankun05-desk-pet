# 开发流程规范

**适用**：desk-pet 主仓功能开发与架构落地  
**原则**：先发现、再方案、审查后动手；动手后审查与测试；能跑通再写文档与提交。

---

## 1. 标准流程

```text
1. 发现问题     现象、影响面、涉及模块
2. 创建方案     目标、非目标、接口/数据、风险、验收标准
3. 审查方案     自审 + （必要时）用户/同伴确认
4. 动手实现     按方案编码，禁止范围蔓延
5. 审查实现     对照方案与验收标准
6. 测试         tsc / eslint / vitest / 必要 e2e
7. 修改完善     失败则回 4–6
8. 更新文档     DESIGN/PLAN/CHANGELOG/用户文档
9. 清理临时文件  脚本、日志、调试产物
10. 整理仓库     目录与命名
11. 提交         见 §3
```

未完成 3 不得大规模改代码；未完成 6 不得宣称完成。

---

## 2. 方案文档要求

每个可交付改动应能对应：

- 背景与问题  
- 目标 / 非目标  
- 方案（模块、接口、数据）  
- 验收标准（可勾选）  
- 风险与回退  

架构级写入 `docs/architecture/`；阶段任务写入 `docs/plan/`。

---

## 3. Git 与提交

- 所有 git / 构建命令在 `desk-pet/` 内执行  
- 提交信息：清晰说明**为什么**  
- Husky 在本机可能异常：按项目既有约定执行；提交前手动 `tsc` / 关键测试  
- **禁止**提交：密钥、`HERMES_HOME` 运行数据、构建产物、临时审计脚本  
- 未要求不 push  

---

## 4. 测试要求

| 类型 | 何时 |
|---|---|
| `tsc --noEmit` | 改 TS 必跑 |
| 相关 vitest | 改逻辑必跑 |
| e2e 冒烟 | 改主链路/Hermes 对接后 |

Hermes 集成相关：至少验证 health、一条 `/v1/runs` 流式、审批回传。

---

## 5. Hermes 相关规范

- 只加插件/MCP/Provider/配置，**不改 core**（见 `docs/architecture/hermes-integration.md`）  
- 锁定官方 tag；升级单独任务  
- LifeKernel 与 Hermes 只通过事件与 API 耦合  

---

## 6. 安全底线

- 权限与危险操作：双保险（Hermes + Electron 审批）  
- 情绪/反思**不得**自动放宽权限  
- 行为/风格自动进化默认关闭（confirm）  

---

## 7. 文档与仓库卫生

- 动工结束：更新 `PLAN.md` 状态、必要时 CHANGELOG  
- 临时脚本进 `scripts/diagnostics/` 或删除，禁止 `tmp-*.cjs` 长期留存  
- 历史材料进 `docs/history/`，顶部标注「历史，不作为当前方案」
